# Paper2Paper 能力缺口与本次修复

审计日期：2026-08-09  
证据来源：NPJ HCC 换癌种 Pilot。

## 一、直接结论

前一版把课题问题拆成“7项产品缺口与候选”，造成了错误印象：仿佛 Paper2Paper
发现了7个产品功能缺陷，又把其中多数留给以后验证。该结构现已删除。

本 Pilot 对 Paper2Paper 产生了三项有直接证据、已经落实的产品修改：

1. **跨 Pilot、跨对话的问题汇集。** 原始事实保留在各 Pilot，经过判断的产品修复
   记录来源和复验，聊天上下文不再充当项目记忆。
2. **逐项判断数据能否完成目标论文中的具体任务。** 数据公开、规模大或字段存在，
   不等于它能承担某幅 Figure 或某项 claim。现在必须先写明数据准备用于发现、验证、
   单细胞定位、空间定位、治疗结局或其他具体任务，再核对决定性组、设计混杂、测量
   空间、运行资源和治疗定义。
3. **基础分析不能从单一论文或代码仓库整套照搬。** 锚点论文、数据生成论文、作者代码、
   官方方法和同类高质量代码各自只提供部分证据；现在必须逐分析步骤建立来源—适配—验收
   链，明确直接复用、修复复用、参考重写或不采用，再用真实数据稳定性完成验收。

其余发现属于 HCC/候选癌种课题、既有能力的正常执行，或当前能力证据边界，不再写成
Paper2Paper 产品缺口。

## 二、哪些事实触发了产品修改

### 修改1：跨对话学习链

真实问题：胃癌与 HCC Pilot 的问题分散在各自 `issues.tsv`，新对话无法稳定知道已有
问题、修复和适用边界；本报告本身还曾把课题困难误写成产品缺口。

已落实：

- `paper2paper learn <repo-root> --write-report` 汇总所有已合并 Pilot；
- `learning/findings.tsv` 只记录归类后的问题、来源、修复和复验；
- 汇总项不会因为出现一次就自动成为产品缺口；
- 测试覆盖跨 Pilot 汇集、未知来源拒绝和课题特有问题不得冒充产品实现。

边界：未合并分支不会自动共享；汇总和测试不证明科学结论正确。

### 修改2：按论文具体用途进行数据预检

本 Pilot 已经取得的事实包括：

- 锚点总体样本很多，但 PVTT 仅2名、MLN仅1名；
- 候选癌种状态可能来自不同队列和平台；
- CRC-atlas 主要对象约31 GB，完整空间归档约299 GiB；
- 已解析的380基因 Xenium panel 缺少多个候选程序关键基因；
- 106个 response 标签来自不同研究、药物和联合方案。

这些不是五个需要分别建设的平台功能，而是同一个 workflow 问题：**此前的数据预检
容易以“数据集整体”为单位，而论文实际需要分别判断它能否完成每项具体任务。**

已落实到 [数据发现与验证](../../../docs/data-discovery.md) 和机器可检查的
`evidence/data_use_checks.tsv`：

1. 分别核对决定性比较组的独立患者数、配对和重复；
2. 输出患者×状态×队列×平台设计表，避免把来源差异写成疾病演化；
3. 对受限 panel/特征空间核对目标对象覆盖，再限定该数据能完成的论文任务；
4. 大文件下载前核对选择文件、磁盘、内存、临时空间和读取方式；
5. 治疗数据按队列冻结药物、时间点和 response 定义，不合并不兼容队列。

所有准备正式使用的数据都要填写这张用途检查表；不同论文只填写与其具体任务有关的
内容，不强迫采用同一种科学设计。校验器只负责阻止“没有检查就写成可用”，不宣称
自动判断科学结论充分。

### 修改3：基础分析的多来源三角补建

本 Pilot 继续执行后发现，原有代码合同能够判断一个 donor 是否有版本、许可证、入口和
smoke，却没有完整说明当以下材料互相矛盾或分别缺一部分时怎样形成最终实现：NPJ HCC 只
报告 CopyKAT/cNMF 结果而不公开代码；CRC 论文和仓库提供 QC/scANVI/SOLO/cNMF 细节，但
SOLO 有静默失败、K 选择和程序合并存在方法问题；官方包只实现算法，不负责患者设计和
目标 Figure。

已落实：

- 新增 [基础分析的方法与代码怎样补齐](../../../docs/foundation-analysis-reconstruction.md)，
  明确锚点、数据论文、官方方法和同类代码的不同作用；
- 每个上游分析只允许直接复用、修复复用、参考重写或不采用四种可审查结论；
- 发生冲突时先保护数学输入、患者独立性和无泄漏，再区分锚点核对与目标论文主实现；
- 用本 Pilot 的
  [第零阶段基础分析审计](phase-zero-foundation-audit.md) 和
  [第零阶段执行规范](../analysis/phase-zero-execution-specification.md) 完成来源、修复、
  输入输出和稳定性冻结。

边界：这项产品方法目前是 `implemented`，不是 `verified`。只有同一 Pilot 在真实 CRC 对象
完成 P0.0–P0.6 并产生 source tables、日志和稳定性证据后，才能证明这套补建方法实际有效。

## 三、哪些不是 Paper2Paper 产品缺口

| 本 Pilot 发现 | 正确归属 | 处理 |
|---|---|---|
| 锚点保留样本清单缺失、旧空间链接失效、作者代码 request-only | 锚点文献限制 | 在目标论文中替代、重建或降低 claim；不修改 Paper2Paper 产品 |
| CRC-atlas downstream 入口缺失、路径写死 | 当前课题代码补足 | 按既有 [代码寻找、组合与重建](../../../docs/code-recovery.md) 修复；只有“多来源怎样共同形成可信基础实现”被抽象为通用方法，具体路径和脚本仍留在本课题 |
| 当前没有单细胞+空间+GPU扰动的完整 Pilot | 能力证据边界 | 只能说这类任务尚未跑通，不能把“缺案例”写成产品功能缺陷 |
| CRC 治疗队列具体能否使用 | 候选路线设计问题 | 只有选定包含治疗问题的路线后才需要冻结具体 estimand |
| 多篇近邻论文是否共同构成实质重复 | 具体路线的发表审计 | 当前路线尚未选定；现有 workflow 已要求审查具体问题—对象—关系—结局—证据组合 |

## 四、原“12项缺口”的最终处理

- 锚点框架提取依赖科学判断：属于产品边界，不假装自动化。
- 多候选数据搜索、公开到解析的证据等级、代码 donor 资格和具体重复审计：Paper2Paper
  已有相应合同；当前缺的是执行，不是新功能。
- 关键组人数、状态—队列混杂、大文件资源、panel 可测性和治疗兼容性：合并为一项
  “按论文具体用途判断数据能不能用”的产品修复，已经写入核心数据指南、workspace
  表结构和校验器。
- 跨 donor 代码拼装：本 Pilot 已实证既有单候选代码合同不足以表达论文、数据代码和官方
  方法的冲突与分工，因而补充了三角补建和冲突裁决；具体 CopyKAT/cNMF 参数仍留在本课题。
- 缺少跨模态验收案例：只记录能力边界，不列为产品缺口。

## 五、当前项目状态，不替用户决定下一步

- `evidence/routes.tsv` 中胃癌、CRC、ICC 三条路线全部仍是 `candidate`；
- `evidence/decisions.tsv` 为空；
- 没有 `selected_route_id`，也没有获批真实运行；
- `analysis/specification.md` 是“如果选择 CRC 进行最低成本预检时”的条件方案，文件
  本身明确说明 CRC 尚未被选定。

因此，Paper2Paper 现在不能写“下一步必须运行 CRC”。CRC 只是基于当前数据审计的
AI 候选建议；在路线比较与建议被审查前，不下载大型对象、不启动 cNMF/Geneformer，
也不把任何癌种写成既定目标论文。

## 六、验收结论

本轮 Paper2Paper 修改已经完成三件事：跨对话不再依赖聊天记忆；数据可用性不再只按
数据集整体判断；基础分析不再从单一论文或仓库整套照搬。它没有证明 NPJ HCC 已成功换
癌种，也没有替用户选择 CRC 或其他癌种；第三项还必须通过本 Pilot 真实运行复验。

后续如果某个真实课题再次暴露现有规则无法处理的问题，应记录具体失败并做最小修复；
不能先生成一串“产品候选缺口”，再要求用户理解或决定它们。
