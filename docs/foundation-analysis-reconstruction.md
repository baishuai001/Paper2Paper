# 基础分析的方法与代码怎样补齐

本指南解决一个会贯穿整篇目标论文的问题：锚点文献给出一种分析，数据生成论文给出另一套
预处理，作者代码不完整或有错误，官方包又只实现算法。Paper2Paper 应怎样组合这些材料，
既不丢掉锚点框架，又不把“有论文/有 GitHub”误写成可靠代码。

这里的“基础分析”按当前论文实际需要定义，可以是单细胞 QC/整合/注释，也可以是 bulk
标准化、空间图像预处理、蛋白组质控、模型特征工程或其他上游步骤；不是固定软件清单。

## 一、先区分四种来源的作用

| 来源 | 最擅长提供 | 不能自动提供 |
|---|---|---|
| 锚点文献 | 问题、证据顺序、Figure 角色、作者使用的参数和结论边界 | 完整实现、未报告选择、可移植代码 |
| 数据生成/同癌种论文 | 数据字段、样本关系、预处理细节、作者标签、实际工程接口 | 目标论文的科学问题、无偏真值、可靠的每一步代码 |
| 方法论文/官方实现 | 算法假设、合法输入、维护版本、参考 API 和基础测试 | 患者切分、目标数据 adapter、Figure 和 claim 验收 |
| 其他高质量同类代码 | 稳定性、合并、留出、统计或工程处理细节 | 可不经许可/适配直接复制的目标实现 |

目标项目代码负责把四者连接起来。不存在“找到一个最佳仓库就结束”的捷径。

## 二、每个分析步骤建立三角补建表

对每个会影响 Figure 或主要结论的步骤，至少记录：

1. **论文证据**：为何需要、对应 Figure/claim、作者报告了什么、缺了什么；
2. **实现证据**：候选代码来源、commit/release、许可证、入口、环境、输入输出和已知问题；
3. **方法证据**：官方/原始方法对数据尺度、统计单位、参数和失败条件的规定；
4. **目标适配**：具体字段、ID、矩阵尺度、分组、患者切分、参数和输出；
5. **验收证据**：fixture、真实 smoke、稳定性、替代方法和 source table。

锚点没有代码时不丢掉分析思路；从官方实现建立算法底座，从数据论文补文件接口，从同类
论文补合理的稳定性/统计细节，再由目标项目编写 adapter 和测试。锚点有代码但质量差时，
也按同一合同验收，不享有豁免。

## 三、先保护科学合同，再决定复用多少代码

在看 donor 代码之前写清：

- 统计单位是患者、样本、切片还是细胞；
- 输入要求原始计数、非负表达、归一化矩阵还是模型 latent；
- 哪些队列用于发现、调参、冻结和验证；
- 哪些参数必须在看结果前冻结；
- 什么现象应当使分析失败或降级；
- 最终 source table 的一行代表什么；
- 哪些 claim 需要独立患者/队列/模态。

donor 代码若违反这些合同，即使能运行也只能借接口或局部逻辑；不能为了少写代码而改变
目标问题。

## 四、代码处理只有四种合法结论

### 1. 直接复用

许可证允许，版本固定，输入输出匹配，非交互运行，测试和真实 smoke 均通过。只做路径和
配置适配，不改变核心算法。

### 2. 修复后复用

保留数据读取、对象组织或算法调用，但修复硬编码路径、静默容错、统计单位、参数、ID
连接或错误 API。每项改动记录“为何改、影响什么、如何验证”。

### 3. 参考后重写

代码无许可证、依赖私有对象、不可移植或算法实现明显有误。只能阅读其处理顺序和文件
含义，目标代码用有许可的官方包重新实现，不复制受限代码。

### 4. 不采用并降低设计

核心算法/输入无法确定，关键数据不存在，也没有可验收替代方案。删除该非必要 Figure、
降低 claim、换数据/方法或停止路线；不能用 AI 猜测填补。

## 五、冲突怎样裁决

常见冲突包括：论文写的方法与仓库代码不同；数据对象与论文样本数不同；官方包更新了
算法；同类论文给出不同阈值。

处理顺序：

1. 保存冲突双方的原始证据，不能静默选择；
2. 首先排除违反数学输入、患者独立性、标识连接或数据泄漏的方案；
3. 区分“精确核对锚点”与“构建目标论文”：前者可运行论文旧版本，后者优先使用冻结且
   受维护的可靠版本；两套结果分开报告；
4. 对仍合理的选择做预先规定的敏感性；
5. 若选择会改变主要结论，提升为用户需要审查的重大决定；
6. 若没有稳定结论，降低 claim，不挑最符合故事的一套。

## 六、可靠性的七层证据

“可靠”必须逐层取得，不能由论文声望、star 数或安装成功替代：

1. **身份**：来源、版本、commit、许可证、引用；
2. **合同**：目标 Figure、输入输出、统计单位、科学不变量；
3. **静态审计**：路径、私有对象、默认参数、容错、随机性、手工步骤；
4. **合成测试**：正确结果和关键反向情形均能检查；
5. **真实 smoke**：代表性真实文件在目标环境非交互运行；
6. **科学稳定性**：患者/队列留出、seed、参数、替代方法和阴性结果；
7. **端到端证据**：manifest→代码→source table→Figure→claim 可追溯。

安装通过只到第 1–3 层；单元测试不等于真实数据运行；一张结果图不等于科学稳定性。

## 七、每次真实论文怎样执行

### 锚点审计时

- 逐 Figure/子图列出基础步骤；
- 判断哪些只是作者实现选择，哪些是不可违反的科学合同；
- 把未报告选择和明显硬伤转成目标论文修复设计。

### 数据与代码预检时

- 检查数据生成论文和样本表，不只检查 accession；
- 搜索锚点、数据论文、官方方法和同类论文代码；
- 为每个候选给出“直接复用/修复复用/参考重写/不采用”；
- 冻结第零阶段执行规范和产物清单。

### 最小真实运行时

- 优先运行最可能推翻路线的基础环节；
- 保存失败，不通过更换阈值制造成功；
- 生成患者/样本级 source table 和诊断图；
- AI 给出继续、缩减或停止判断，而不是让用户从日志里猜。

### 正式分析中

- 同一基础合同继续约束所有后续 Figure；
- 新数据或新代码必须重新执行身份、适配和稳定性检查；
- 若真实运行暴露通用失败，先修当前论文，再按双循环规则写入跨 Pilot 学习链。

## 八、哪些属于 Paper2Paper，哪些留在具体课题

Paper2Paper 应长期保留的是：四类来源分工、三角补建、四种代码处置、冲突裁决、七层可靠
证据和真实运行后的双循环复验。

具体课题保留的是：某癌种 QC 阈值、某 H5AD 字段、某 CNA 参数、某 cNMF K、某 marker、
某服务器资源和某程序合并结果。只有去掉论文专名后仍会导致其他项目重复犯错，而且已有
有限可检查的补法，才把课题问题升级为 Paper2Paper 规则。

## 九、真实 CRC 运行验证出的通用细节

本指南已在 31 GB CRC H5AD、CopyKAT、SCEVAN 和 cNMF 上完成第一次真实复验。它进一步
确认，代码 donor 的验收不能只检查“函数名存在”和“包能安装”：

- 用代表性真实输入读取实际函数 formals、合法稀疏矩阵类和真实输出路径；文档参数、安装
  API 和内部硬编码路径可能不同；
- 对每个中间文件冻结 shape/orientation、ID 唯一性、数值类型和维度不变量；cNMF spectra
  的一次错误转置就会把基因当程序，并把小计算变成高内存错误计算；
- 大型上游文件只在资源入口完整计算一次 SHA256。下游读取已通过的收据，同时复核解析
  路径和字节数；不要每一步重复扫描几十 GB，也不能只凭文件名继承身份；
- “跨 seed 稳定”只说明同一输入上的算法重复性。患者/数据集贡献、留出复现和比较设计
  仍可能揭示稳定的技术伪影，因此不能把软件 stability 直接写成科学稳定性。
- K 尚未冻结时，只报告每个 K 内的一对一程序匹配。不能把跨 seed、相邻 K 和不同输入的
  匹配边直接做传递并集来宣布“程序家族”；这种图合并会经由中间节点把同一运行、同一 K
  的多个不同程序错误并入一个家族。跨 K 合并必须等 K 冻结后另设有冲突约束的合同。

这些规则来自真实运行和保留的失败日志，不是新增抽象层。具体 API、样本、K 和数值仍留在
对应 Pilot。

## 十、停止扩建的条件

当当前目标论文的基础分析已有合格实现、真实数据、source table 和稳定性证据时，立即回到
后续 Figure 和稿件主循环。不要为了覆盖所有组学、软件或未来论文，继续增加与当前目标无关
的框架、schema 或测试。
