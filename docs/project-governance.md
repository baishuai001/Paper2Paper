# Paper2Paper 项目治理

## 治理目标

Paper2Paper 的记录和 Git 历史应让用户能够回答：

- 当前在分析哪篇文献、哪条路线；
- AI 做了什么，依据是什么；
- 哪些事实真实下载或运行过；
- 哪些只是结构校验、暂定判断或待验证建议；
- 某次产品变更影响了哪些真实文献；
- 为什么继续、修正、晋升或停止；
- 当前工作是否仍在推进论文，而不是优化平台本身。

## 决策责任

### AI 可以自主完成

- 只读文献、数据、代码和仓库审计；
- 在已批准范围内下载公开数据、安装依赖和运行分析；
- 构建有依据的候选路线组合；
- 编写和测试模块适配器；
- 记录失败、结果、限制和推荐；
- 对低风险、可逆、范围明确的实现缺陷进行修复。

### 用户必须批准

- 从候选中选择正式论文路线；
- 中心问题、主要结局、claim ceiling 和投稿用途；
- 结果出现后的中心 reroute；
- 明显扩大时间、数据、计算或协作范围的决定；
- module/core 的高影响语义变更；
- 正式稿件和发布。

AI 不能用一个模糊总分替用户决定，也不能把所有判断甩给用户。AI 必须先给出推荐、依据、不确定性、备选和风险，再请求批准。

## 一个 PR 一个层次

每个 PR 必须声明唯一的主要层次：

### Core PR

可以包含：通用 schema、校验、CLI、核心测试和相应文档。

不能包含：某篇 Pilot 的新科学结果、某个 signature 的预期数值或正式稿件改写。

### Module PR

可以包含：一个模块的合同、实现、许可记录、测试和 module registry 行。

不能包含：将某篇文献路线直接选为正式稿件，或顺手改变不相关 core 纪律。

### Pilot PR

可以包含：一篇真实锚点的审计、路线、数据/代码证据、运行和 finding。

不能包含：把该 Pilot finding 直接实现成 core 通用规则。Pilot PR 只提交晋升建议和来源证据。

### Manuscript-project PR

可以包含：一条已批准正式路线的规范、完整分析、Figure、结果解释和稿件。

不能包含：为其他论文设计通用平台功能。

`registries/` 是索引而非第五层；某个层次的 PR 可以更新描述该层新增资产所必需的 registry 行，但不能借 registry 更新夹带另一个层次的实现或科学结果。

### 跨层问题的 PR 顺序

一个 Pilot 暴露 core/module 缺陷时，按顺序拆分：

1. Pilot PR：保存真实观察、当前实例处理和晋升建议；
2. Module PR：若是同类分析能力，提取合同、实现和测试；
3. Core PR：若确实跨模块通用，新增最小规则和核心测试；
4. Pilot 回归 PR：用新版本产生新的 run 并更新影响；
5. Manuscript PR：只有用户批准路线后才进入正式分析。

不要在一个巨大 PR 中同时改 schema、重写 Pilot 结果、改变路线选择和生成稿件。这样无法判断每项变更的依据，也无法安全回滚。

## PR 必填信息

每个 PR 描述至少包括：

- **目标层**：core/module/pilot/manuscript-project；
- **要解决的真实问题**：来源文献、finding 或正式稿件需求；
- **范围内文件**和明确的范围外内容；
- **证据层级**：结构、单元、真实数据、科学审查分别完成到哪；
- **受影响对象**：capability、module、Pilot、route、run 或 manuscript；
- **实际运行的测试**与未运行原因；
- **不声称什么**：尚未验证的模态、癌种、数据或结论；
- **回滚/停止条件**；
- **需要用户决定的事项**。

PR 标题应描述结果和层次，而不是使用“全面验证”“彻底完成”等超范围词语。

## 选择性回归

每项变更先查 `regression_cases.tsv`，再确定测试范围。

| 变更 | 最低回归范围 |
| --- | --- |
| Core schema/校验 | 核心单元测试、受影响 workspace 结构校验、映射到该 control 的案例 |
| Module 合同/实现 | 模块单元与合成测试、参考真实案例、已登记迁移/失败案例 |
| Pilot 数据或代码 | 当前 Pilot 的 checksum、聚焦测试、受影响 run 和结果比较 |
| 正式分析规范 | 当前 manuscript-project 的冻结规范检查和全部受影响 Figure |
| 仅文档术语 | 链接、术语和与 schema 的一致性检查；不伪称真实数据回归 |

全量测试可以作为额外保障，但不能替代影响分析。随着 Pilot 增多，默认重跑所有真实数据既浪费资源，也掩盖“究竟哪个能力被验证”。

回归必须产生新 run 或新的验证记录。旧成功输出不能被覆盖；新旧不一致时先检查输入版本、合同和参数，再更新科学解释。

## 防循环确认审查

每次路线选择、模块晋升或核心规则合并前，审查以下问题。

### 数据与结果

- 候选生成和最终验证是否使用同一结局或同一患者？
- 队列是否参与过特征筛选、调参或 cutoff？
- expected result 是否来自同一实现和同一次运行，缺少独立依据？
- 事后新增分析是否明确标为探索性？

### 模块与能力

- 来源 Pilot 是否既提出规则又被当作唯一迁移验证？
- 合成测试是否被误写成真实数据证明？
- 模块成功是否只证明运行，而没有检查科学不变量？
- 新适用范围是否超出实际 reference/transfer cases？

### 论文与重复发表

- 最近发表检索是否覆盖疾病同义词、对象同义词、结局和主要方法？
- “换了一个名字”是否掩盖中心问题和证据链实质相同？
- 训练复现是否被包装成新发现？

发现循环确认时，应重新划分 discovery/validation、增加独立证据、降低 claim 或停止；不能通过修改标签让检查通过。

## 版本和历史

- Core 使用语义化版本；破坏 schema 或状态含义时提升 major 版本并提供迁移说明。
- Module 独立版本化；输入尺度、统计单位、公式或输出语义变化视为破坏性变更。
- Pilot 每次真实执行使用唯一 run ID，保留失败、invalidated 和 superseded 记录。
- Manuscript project 冻结分析版本；查看结果后的高影响修改产生新版本和用户决定。
- `deprecated` 的 rule/module 保留历史、原因和受影响项目，不从审计链中消失。

## 平台工作准入检查

提出新的 schema、模块、自动化或 registry 字段前，必须回答：

1. 它解决哪个正在进行的真实 Pilot/稿件问题？
2. 不实现会导致错误、阻断还是仅仅“不够漂亮”？
3. 应在 Pilot、module 还是 core 解决？
4. 能否写出明确合同和测试？
5. 哪个第二案例可以验证适用范围？
6. 实现和维护成本是否小于对论文路线的价值？

如果没有真实问题、无法测试或只是为未来假想场景准备，记录在 backlog，不进入当前 PR。

## 停止平台建设并转入论文的条件

满足以下条件后，当前迭代只允许修复正式论文的真实阻断项：

- 一条路线已由用户批准并建立 manuscript-project；
- 必需数据文件、字段和 ID 已实际审计；
- 必需模块在目标环境通过真实输入；
- 最低主 Figure 和 source table 能稳定生成；
- 最近发表没有发现实质重复；
- claim ceiling、falsifier 和停止条件清楚；
- 剩余任务主要是完整运行、结果解释和写作。

“还可以再抽象一层”“以后可能用到”或“代码可以更漂亮”都不是继续平台建设的充分理由。

## 交付给用户的最低说明

每次阶段性交付必须用普通语言说明：

- 已经得到的结果；
- 这些结果基于什么数据和代码；
- 哪一层证据通过；
- 仍然不知道什么；
- 风险会怎样影响论文；
- AI 的推荐及依据；
- 下一步是否需要用户批准。

不能只报告 commit、PR、状态码或内部术语。用户不应通过不断追问才能知道项目具体做了什么。
